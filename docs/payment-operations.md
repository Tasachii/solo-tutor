# การรับเงิน Pro และหลักฐานรายได้แบบทำมือ

ระบบปัจจุบันใช้ PromptPay และการตรวจรายการเดินบัญชีด้วยคน ไม่มีการตัดเงินอัตโนมัติ และยังไม่เชื่อม payment gateway ตัวเลขสำหรับ pitch จะนับเป็นรายได้ที่ยืนยันแล้วต่อเมื่อมีหลักฐานธนาคารบันทึกผ่าน RPC ในเอกสารนี้เท่านั้น คำขอที่กดอนุมัติด้วยฟังก์ชันรุ่นเก่ายังทำงานได้เพื่อความเข้ากันได้ แต่จะแสดงเป็น `legacy_unverified` และไม่รวมในยอด verified gross/net

ตารางหลักฐานและ RPC เปิดเฉพาะ `service_role` ห้ามนำ service-role key ไปไว้ในเว็บ เบราว์เซอร์ สคริปต์สาธารณะ หรือภาพประกอบการ pitch ค่าอ้างอิงธนาคารและชื่อผู้ตรวจเป็นข้อมูลปฏิบัติการ ให้เปิดดูเฉพาะคนที่ทำ reconciliation หรือจัดการคืนเงิน

## รับเงินและเปิด Pro

1. เปิดรายการคำขอที่ยังรอตรวจ

   ```sql
   select r.id, u.email, r.months, r.amount, r.created_at
   from public.plan_requests r
   join auth.users u on u.id = r.provider_id
   where r.status = 'pending'
   order by r.created_at;
   ```

2. เทียบชื่อ/เวลา/ยอดในรายการเดินบัญชีจริง ยอดต้องตรงกับ `amount` จากเซิร์ฟเวอร์ ห้ามใช้รูปสลิปอย่างเดียวเป็นข้อยืนยัน และห้ามสร้างเลขอ้างอิงสมมติ

3. เรียก wrapper ครั้งเดียว โดยใช้เลขอ้างอิงธุรกรรมจากธนาคารและป้ายชื่อผู้ตรวจที่ทีมตามตัวได้

   ```sql
   select * from public.approve_plan_request_verified(
     '<request id>',
     '<bank transaction reference>',
     799,
     '2026-09-08T09:41:00+07:00',
     '<operator label>'
   );
   ```

   ค่าเวลาต้องเป็นเวลาที่รายการเกิดในธนาคารจริงพร้อมเขตเวลา เช่น `+07:00` สำหรับเวลาไทย ไม่ใช่เวลาที่มาเปิด SQL Editor และต้องเป็นเวลาปกติที่ไม่เกินเวลาเซิร์ฟเวอร์มากกว่า 5 นาทีซึ่งเผื่อความคลาดเคลื่อนของนาฬิกา ฟังก์ชันตรวจว่ายอดรับจริงตรงกับยอดคำขอ บังคับเลขอ้างอิงไม่ซ้ำ ออกเลขใบเสร็จ เปิดแพ็ก และบันทึกหลักฐานใน transaction เดียว ถ้าขั้นใดผิดทั้งหมดจะ rollback คำขอยังคง pending ระบบเก็บ `verified_at` จากเวลาเซิร์ฟเวอร์แยกไว้เป็น audit ว่าทีมตรวจเมื่อใด

4. ตรวจผลลัพธ์ `plan_until` และ `receipt_no` แล้วให้ครูกดซิงก์หรือเปิดแอปใหม่ ครูจึงเห็นแพ็กและใบเสร็จค่าสมาชิก

ห้ามเรียก `approve_plan_request` รุ่นเดิมสำหรับยอดใหม่ เพราะไม่มีหลักฐานธนาคารและจะไม่เข้าตัวเลข verified หากเคยอนุมัติผ่านรุ่นเดิม ให้เก็บเป็น legacy ตามจริง ห้ามสร้างหลักฐานย้อนหลังจากการคาดเดาหรือสลิปที่ยังไม่ได้เทียบรายการเดินบัญชี

## คืนเงิน

คืนเงินจริงผ่านธนาคารให้สำเร็จก่อน แล้วจึงบันทึกหลักฐาน ห้ามเรียก RPC เพื่อแทนการโอนเงินจริง

1. หา payment evidence ต้นทาง

   ```sql
   select e.id, e.bank_reference, e.amount, e.occurred_at, e.verified_at, r.receipt_no
   from public.plan_financial_evidence e
   join public.plan_requests r on r.id = e.plan_request_id
   where e.evidence_type = 'payment' and r.receipt_no = '<receipt number>';
   ```

2. หลังธนาคารยืนยันการคืนเงินจริง เรียก

   ```sql
   select * from public.record_plan_refund(
     '<payment evidence id>',
     '<bank refund transaction reference>',
     100,
     '2026-09-10T14:05:00+07:00',
     '<operator label>'
   );
   ```

เวลาคืนเงินต้องมาจากรายการธนาคารพร้อมเขตเวลา ต้องไม่อยู่ก่อนเวลารับเงิน และต้องไม่เกินเวลาเซิร์ฟเวอร์มากกว่า 5 นาทีซึ่งเผื่อความคลาดเคลื่อนของนาฬิกา เลขอ้างอิงคืนเงินต้องไม่ซ้ำ จำนวนต้องมากกว่าศูนย์ และยอดคืนสะสมต้องไม่เกินยอดรับของ payment นั้น หลักฐานเป็น append-only แก้หรือลบภายหลังไม่ได้ หากกรอกผิดให้หยุดและตรวจฐานข้อมูลกับรายการธนาคารก่อนออกแบบรายการแก้ไขใหม่

การบันทึก refund ไม่โอนเงิน ไม่พัก ไม่ยกเลิก และไม่ลดวันของแพ็กโดยอัตโนมัติ หากนโยบายธุรกิจภายหลังกำหนดให้คืนเงินแล้วต้องเปลี่ยนสิทธิ์ ต้องออกแบบและอนุมัติกระบวนการนั้นแยกต่างหาก

## ตัวเลขสำหรับ pitch

รัน [pitch-metrics.sql](../scripts/pitch-metrics.sql) ใน SQL Editor ผลลัพธ์แสดง:

- จำนวน payment ที่มีหลักฐานธนาคาร และจำนวนลูกค้าที่บัญชียังเชื่อมอยู่พร้อมยอดสุทธิหลังคืนเงินมากกว่าศูนย์
- verified gross, refund และ net แยกรายเดือนตาม `occurred_at` ของธนาคารในเขตเวลา `Asia/Bangkok` และยอดรวม การตรวจย้อนหลังจึงไม่ย้ายรายได้มาอยู่เดือนที่ผู้ตรวจเปิด SQL
- approved รุ่นเก่าที่ไม่มีหลักฐานในคอลัมน์ `legacy_unverified` แยกจากรายได้ยืนยันแล้ว
- cohort ต่อเดือนที่ 2 จาก payment ที่ยืนยันแล้ว มียอดสุทธิมากกว่าศูนย์ และบัญชียังไม่ถูกลบ
- การเปิดแอป 30 วันเป็น engagement เท่านั้น ไม่ถูกนำมาสร้างรายได้

เมื่อบัญชีครูถูกลบ `provider_id` และ note ใน plan request จะถูกถอดออก แต่แถวใบเสร็จและหลักฐานการเงินขั้นต่ำยังคงอยู่ จึงนับ gross/refund/net ต่อได้โดยไม่รวมในจำนวนลูกค้าที่ระบุตัวตนได้ หลักฐานยังมีเลขอ้างอิงธนาคารและป้ายผู้ตรวจ จึงไม่ควรเรียกว่า anonymous และเอกสารนี้ไม่ได้กำหนดระยะเวลาเก็บตามกฎหมาย ต้องให้ผู้เชี่ยวชาญกำหนด retention และสิทธิ์เข้าถึงก่อนรับเงินจริง

ระบบนี้เหมาะกับลูกค้ารุ่นแรกและ Supabase Free ที่ทีมตรวจยอดด้วยมือ เมื่อปริมาณรายการทำให้ reconciliation รายวันหรือการคืนเงินเริ่มผิดพลาด ให้ประเมิน gateway จาก recurring payment, webhook ที่ตรวจลายเซ็นได้, refund API, reconciliation/export, ใบเสร็จภาษี, ค่าธรรมเนียม และข้อกำหนดนิติบุคคลก่อนเลือกผู้ให้บริการ
