## PART A · ชั้นข้อมูล — เตรียมเผื่อมีหลังบ้าน

ตอนนี้ state ทั้งก้อนอยู่ใน `useReducer` + localStorage ผ่าน `core/store.tsx`
เป้าหมาย: **แยก "ที่เก็บข้อมูล" ออกจาก "ตรรกะ"** ให้วันหลังเสียบ Supabase/Firebase ได้โดยไม่ต้องแก้หน้าจอเลยสักหน้า — แต่**วันนี้ยังทำงานแบบ static เหมือนเดิมทุกอย่าง**

### A1 · สร้าง `src/data/`

```
src/data/
  types.ts      Repo interface + DTO
  local.ts      LocalRepo — localStorage (ของที่ใช้จริงวันนี้)
  memory.ts     MemoryRepo — ใช้ในเทสต์
  index.ts      เลือก repo จาก env / config
```

- นิยาม `interface Repo` ที่ **ทุก method เป็น async (คืน Promise)** ตั้งแต่วันนี้ แม้ LocalRepo จะ resolve ทันที — จะได้ไม่ต้องไล่แก้ทั้งแอปตอนต่อ server จริง
- method ที่ต้องมีอย่างน้อย: `load()`, `save(state)`, `patch(entity, id, changes)`, `clear()`
- ห้ามให้คอมโพเนนต์ไหนแตะ `localStorage` ตรง ๆ อีก — ผ่าน repo เท่านั้น
- `core/store.tsx` เรียก repo ตอน mount และหลังทุก action (write-behind, debounce 300ms)
- เพิ่ม state `status: 'loading' | 'ready' | 'error'` ใน StoreProvider แล้วให้ AppShell แสดง skeleton ตอน loading — วันนี้แทบไม่เห็น แต่ตอนต่อ server จะได้ไม่พัง

### A2 · ปรับ data model ให้พร้อมเป็น multi-user

ใน `core/types.ts`:
- `schemaVersion: 3` → `4` พร้อมเขียน migration ใน `data/local.ts` (v3 → v4 ต้องไม่ทำข้อมูลเดิมหาย)
- เพิ่ม `updatedAt: ISODate` ให้ทุก entity ที่แก้ไขได้ (Subject, Invoice, Message, Client) — เตรียมไว้ทำ conflict resolution
- เพิ่ม `providerId: string` ให้ทุก entity ระดับบนสุด — วันนี้ hardcode เป็น `'local'` วันหลังคือ user id จริง
- เปลี่ยนวิธี gen id เป็น `crypto.randomUUID()` (มี fallback) แทน counter — server จะได้ไม่ชนกัน
- แยก `counters` (เลขที่ใบเสร็จ) ออกมาเป็น entity ของตัวเอง เพราะเป็น shared counter ที่ต้อง atomic ตอนมี server

### A3 · แยก selector ออกจาก component

- ย้าย logic คำนวณทุกอย่างที่ตอนนี้อยู่ใน `.tsx` ไปที่ `core/selectors.ts`
- คอมโพเนนต์เรียก selector อย่างเดียว ห้ามคำนวณเงินหรือวันเองในไฟล์ `.tsx`
- เขียนเทสต์ให้ selector ใหม่ทุกตัว

## PART B · Remodel UI/UX ทุกหน้า

**หลักคิด: นี่คือแอปที่ติวเตอร์เปิดบนมือถือ ระหว่างสอน มือข้างเดียว** — ไม่ใช่ dashboard บนคอม

### B1 · Design system ก่อนแตะหน้าจอ

สร้าง `src/styles/tokens.css` + `src/styles/base.css` แล้วให้ทุกหน้าใช้จากตรงนี้เท่านั้น:
- **สี**: ปรับ palette ให้มีน้ำหนักและมีตัวตนกว่าเดิม — 1 สีหลัก + 1 สีรอง + สีสถานะ (จ่ายแล้ว / ค้าง / เกินกำหนด) · ต้องผ่าน contrast AA ทั้ง light และ dark
- **ตัวอักษร**: type scale 6 ระดับ ฟอนต์ไทยอ่านง่ายบนมือถือ (Anuphan ที่ใช้อยู่ok) — กำหนด line-height ให้พอดีกับสระบน/ล่างภาษาไทย
- **ระยะ**: spacing scale 4/8/12/16/24/32 · radius 3 ระดับ · elevation 2 ระดับ
- **hit target ทุกปุ่มไม่ต่ำกว่า 44px** — ข้อนี้สำคัญสุด ตอนนี้หลายปุ่มเล็กเกิน
- ลบ inline style ที่กระจัดกระจายออกให้หมด แทนด้วย class จาก design system

### B2 · โครงนำทางใหม่

## PART C · ฟีเจอร์ที่ต้องเพิ่ม

### C0 · บิลต้องจ่ายได้จากในข้อความ ไม่ต้องกดลิงก์  **[ต้องมีก่อนวันแข่ง]**
สถานะวันนี้ (เช็คโค้ด 6 ก.ย.): ปุ่มส่งเปิด LINE ผ่าน `line.me/R/share` ได้แล้ว (fallback คัดลอก) · โหมด real ฝังเอกสารบิลไว้ใน hash URL (`#/document/<token>`) เปิดข้ามเครื่องได้โดยไม่มีหลังบ้าน — ดีมาก แต่**การจ่ายเงินยังต้องกดลิงก์ก่อนถึงจะเห็น QR** ซึ่งขัดกับ insight ว่าผู้ปกครองไม่ชอบกดลิงก์ (`renewalText` ใส่เลขพร้อมเพย์ในข้อความแล้ว แต่ `invoiceText` / `reminderText` ยังไม่ใส่)
- ทุกข้อความที่ขอเงิน (`invoice`, `reminder`, `renewal`) ในโหมด real ต้องมี **ยอด + เลขพร้อมเพย์ + ชื่อผู้รับ** เป็นตัวหนังสือในข้อความเสมอ — ลิงก์เอกสารเป็นแค่ "ดูรายละเอียด" ไม่ใช่ทางเดียวที่จะจ่าย
- เพิ่มปุ่ม "ส่งรูป QR" ต่อจากส่งข้อความ: สร้าง PromptPay QR เป็น PNG แล้วแชร์ผ่าน `navigator.share({ files })` (แบบเดียวกับ `app/backup.ts`) — เป็นขั้นที่ 2 ที่ครูเลือกทำได้ ไม่บังคับ
- ทดสอบบนมือถือจริง: ความยาวลิงก์ `#/document/<token>` (MAX_TOKEN 16000) กับขีดจำกัดของ `line.me/R/share?text=` — ถ้ายาวเกิน ต้องมี fallback เป็นคัดลอกอัตโนมัติพร้อม toast บอกครู ห้ามเงียบ
- README ระบุแล้วว่าลิงก์เพิกถอนไม่ได้และใครมีลิงก์ก็อ่านได้ — ให้แสดงคำเตือนนี้ครั้งเดียวตอนเปิดโหมด real และเขียนไว้ใน FAQ "ข้อมูลอยู่ไหน"

### C0.5 · ตรวจสลิปจริง — วางเป็น adapter
- สร้าง `interface SlipVerifier { verify(image, expected): Promise<Result> }` ใน `core/`
- `DemoVerifier` = `rollSlip` เดิม (ผลผูกกับเลขใบแจ้ง) · `ApiVerifier` = ยิง API ตรวจสลิป (EasySlip / SlipOK / Thunder ~0.14–0.42 บาท/ใบ) — ยังไม่ต้องต่อจริงรอบนี้ แค่ให้เสียบได้โดยไม่แก้หน้าจอ
- แสดงชัดใน UI ว่าผลตรวจมาจาก "จำลอง" หรือ "ตรวจจริง"

### C1 · ตารางสอน + เลื่อน/ยกเลิกคลาส  **[ต้องมีก่อนวันแข่ง]**
เป็นสิ่งที่ผู้ให้สัมภาษณ์ขอเองบ่อยที่สุด (3 ใน 8 คน) โดยเราไม่ได้ถามนำ
- แตะคาบใน Today → เลื่อน (เลือกวัน/เวลาใหม่) หรือ ยกเลิก
- บันทึกเป็น event ใน ledger (`unit_rescheduled` / `unit_cancelled`) ไม่ใช่แก้ตัวเลขในหน้าจอ
- **ห้ามกระทบยอดบิล** จนกว่าคาบนั้นจะถูกยืนยันจริง
- เลื่อนแล้ว AI ร่างข้อความแจ้งผู้ปกครองเข้ากล่องรอส่ง (ครูกดส่งเอง)
- หน้า "สัปดาห์นี้" แบบ list ง่าย ๆ — ยังไม่ต้องทำปฏิทินเต็ม

### C2 · สรุปพัฒนาการนักเรียน  **[ต้องมีก่อนวันแข่ง]**
โหวตอันดับ 2 ในแบบสอบถาม (12 จาก 50) — เป็นของใหม่ที่เราไม่ได้วางแผนไว้
- ช่องบันทึกสั้น ๆ ต่อคาบ (หัวข้อที่สอน + โน้ต 1 บรรทัด) กดจากหน้า Today หลังยืนยัน
- สิ้นเดือน AI ร่างสรุปจากโน้ตเหล่านั้น → เข้ากล่องรอส่ง ส่งพร้อมบิลได้
- ผู้ปกครองเห็นในหน้าเดียวกับบิล

### C3 · ให้ผู้ปกครองเห็นการเข้าเรียนแบบ real-time
- หน้า ClientPreview แสดงจำนวนครั้งที่เรียนไปแล้วเดือนนี้ อัปเดตทุกครั้งที่ครูยืนยัน
- ตอบคำถาม "ลูกเรียนไปกี่ครั้งแล้ว" ที่ 52% ของผู้ตอบเจอทุกเดือน โดยครูไม่ต้องตอบเอง

### C4 · เตือนตารางสอนประจำวัน
- สรุปคาบของวันนี้ให้ครูตอนเปิดแอปครั้งแรกของวัน
- ยังไม่ต้องทำ push notification (ต้องมี server) — ทำเป็น in-app banner ไปก่อน

### C5 · ปรับปรุงแพ็ก
- เตือนล่วงหน้าหลายระดับ: เหลือ 3 / เหลือ 1 / หมดแล้ว
- จับเคส "หมดแล้วยังมาเรียน" ให้เด่นขึ้นในหน้า Today

### C6 · ประวัติรายรับ
- กราฟรายเดือนย้อนหลัง 6 เดือน (ใช้ recharts หรือ SVG เขียนเอง — อย่าลง lib ใหญ่)
- เทียบเดือนนี้กับเดือนที่แล้ว

### C7 · ตั้งวันครบกำหนดชำระรายคน
- ตอนนี้ใช้ `dueDays` ค่าเดียวทั้งระบบ — ให้ตั้งต่อคนได้ (default ยังเป็นค่ากลาง)

**ยังไม่ทำในรอบนี้:** ตารางว่างออนไลน์ให้ผู้ปกครองจองเอง, โหมดทีมหลายครู, นักเรียนกลุ่ม, ฝั่งส่งการบ้าน, ใบกำกับภาษี, อาชีพที่ 2, ระบบจ่ายเงินจริง

## PART D · คุณภาพและวิธีทำงาน

**ต้องผ่านก่อน commit ทุกครั้ง**
```
npm run build && npm run test && npm run e2e
```

**เทสต์ที่ต้องเพิ่ม**
- repo layer: load/save/migrate v3→v4 ต้องไม่ทำข้อมูลหาย
- เลื่อนคลาสแล้วยอดบิลต้องไม่เปลี่ยน (สำคัญสุด — เป็นจุดที่พังง่าย)
- สรุปพัฒนาการ: มีโน้ต 0 อัน ต้องไม่ร่างข้อความเปล่า
- แพ็ก: เตือน 3 ระดับยิงถูกจังหวะ
- e2e: เดินเส้นทาง ยืนยัน → เลื่อนคลาส → ปิดเดือน → ส่งบิล → ตรวจสลิป → ใบเสร็จ

**ลำดับการทำ — commit แยกตามนี้ ห้ามรวบเป็นก้อนเดียว**
1. `refactor(data)` — PART A ทั้งหมด (ยังไม่แตะ UI, เทสต์เดิมต้องผ่านหมด)
2. `feat(ui)` — B1 design system + tokens
3. `feat(ui)` — B2 navigation + B3 ทีละหน้า (commit ละหน้า)
4. `feat(pay)` — C0 + C0.5
5. `feat(schedule)` — C1
6. `feat(progress)` — C2
7. `feat(client)` — C3
8. `feat(app)` — C4–C7
9. `docs` — อัปเดต README ให้ตรงกับของจริง
